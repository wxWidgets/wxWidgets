Binary Compatibility and wxWidgets
==================================

Purpose
-------

This is a broad technote covering all aspects of binary compatibility with
wxWidgets.

Releases
--------

General overview of releases can be found in [wxWidgets naming conventions](about-platform-toolkit-and-library-names.md),
but for completeness the wxWidgets release version number is as follows:

	2.6.2

Where

	  2      6      2
	Major  Minor Release

(i.e. Major.Minor.Release).

All versions with EVEN minor version component (e.g. 2.8.x, 3.0.x etc.)
are expected to be binary compatible (ODD minors are development versions
and the compatibility constraints don't apply to them). Note that by
preserving binary compatibility we mean BACKWARDS compatibility only,
meaning that applications built with old wxWidgets headers should continue
to work with new wxWidgets (shared/dynamic) libraries without the need to
rebuild. There is no requirement to preserve compatibility in the other
direction (i.e. make new headers compatible with old libraries) as this
would preclude any additions whatsoever to the stable branch. But see
also the section about `wxABI_VERSION`.


What kind of changes are NOT binary compatible
----------------------------------------------

[The KDE guide](https://community.kde.org/Policies/Binary_Compatibility_Issues_With_C%2B%2B)
is a good reference.


The changes that are NOT binary compatible:

- Adding a virtual function
- Adding, removing or reordering base classes
- Changing the name of any function or variable
- Changing the signature of a virtual function (adding a parameter,
  even a default one)
- Changing the order of the virtual functions in a class ("switching" them, etc.)
- Changing access privileges of a function: some compilers (among which MSVC)
  use the function access specifier in its mangled name. Moreover, while
  changing a private function to public should be compatible (as the old
  symbol can't be referenced from outside the library anyhow), changing a
  virtual private function to public is NOT compatible because the old symbol
  is referenced by the virtual tables in the executable code and so an old
  program compiled with MSVC wouldn't start up with a new DLL even if it
  doesn't use the affected symbol at all!
- Adding a member variable
- Changing the order of non-static member variables
- Changing an inline function in a way which depends on the new behaviour
  of the library: inline functions are compiled into the application code,
  so the applications compiled with the old headers keep using the old
  version of the function


Changes which are compatible
----------------------------

- Adding a new class
- Adding a new non-virtual method to an existing class
- Adding a new constructor to an existing class
- Adding a new event type
- Adding new elements to the end of an enum, as long as neither the values
  of the existing elements nor the size of the enum change
- Overriding an existing virtual function in an existing class, but see
  the caveat below
- Anything which doesn't result in ABI change at all, e.g. adding new
  macros, constants and, of course, private changes in the implementation

Note that all new symbols must be guarded by `wxABI_VERSION` checks and
added to `version-script.in`, see below.


Overriding existing virtual functions
-------------------------------------

Overriding an existing virtual function in a class which didn't override it
before doesn't break the ABI, but the new override is _not_ used for the
objects of the classes deriving from it which were compiled with the old
headers. For example, if `wxCalendarCtrl` starts overriding `MSWWindowProc()`
in a later 3.4.x release, an application class `MyCalendar` deriving from
`wxCalendarCtrl` compiled with 3.4.0 headers still has `wxControl` version of
this function in its virtual table, as this table is generated by the compiler
when compiling the application code, and so never calls the new override.

This is fine when the only consequence of this is that the classes in the
application code keep the old behaviour, but care needs to be taken to avoid
inconsistencies, e.g. when the new override must be used together with some
other change. When this is a problem, use the extension hooks described below
instead, as they don't suffer from this problem.


Adding data to existing classes
-------------------------------

New member variables can't be added to the existing classes, but the classes
deriving from `wxWithExtraData`, declared in `wx/extradata.h`, can store any
number of objects of arbitrary types instead. Currently this includes:

- `wxEvtHandler` and so all windows and other event handlers
- `wxEvent` and all events
- `wxDataObject` and all classes deriving from it
- `wxAuiDockArt`, `wxAuiTabArt`, `wxAuiToolBarArt` and `wxRibbonArtProvider`
- `wxCaret`

To use it, define a class deriving from `wxExtraData`, declared in the private
`wx/private/extradata.h` header, and use `wxGetExtraData()` to access it,
e.g.

```cpp
// In src/msw/calctrl.cpp:
#include "wx/private/extradata.h"

namespace
{

class wxCalendarCtrlExtraData : public wxExtraData
{
public:
    int m_newField = 0;
};

} // anonymous namespace

void wxCalendarCtrl::SomeFunction()
{
    // This creates the extra data object if it doesn't exist yet.
    wxGetExtraData<wxCalendarCtrlExtraData>(this)->m_newField = 17;

    // And this one just returns null if it doesn't exist.
    if ( auto* data = wxGetExtraDataIfExists<wxCalendarCtrlExtraData>(this) )
        ...
}
```

Notes:

- The extra data is destroyed in `wxWithExtraData` destructor, i.e. after the
  destructor of the class using it has already run, so its destructor must
  not use the object it is associated with. `wxResetExtraData()` can be used
  to destroy it earlier if necessary.
- When an object is copied, its extra data is copied only if it derives from
  `wxCloneableExtraData`, otherwise it is not copied at all.
- Each extra data class must only be used from the code in a single wx
  library, as the key identifying it is not shared between them.


Adding virtual functions to existing classes
--------------------------------------------

The equivalent of adding a new virtual function can be achieved by using
`wxObject::WXExtensionHook()`, which can be used with all classes deriving
from `wxObject`. The default implementation of this function calls the
handler registered for the given hook id and the class of the object, as
determined by its `wxClassInfo`, or its closest base class for which a handler
is registered. Because of this, it works correctly for the classes defined in
the application code and compiled with the older headers too, unlike the new
overrides of the existing virtual functions.

To add a new hook, see the detailed instructions in the private
`wx/private/extensionhook.h` header, but basically:

1. Add a new element to `wxExtensionHookId` enum.
2. Specialize `wxExtensionHookTraits` for it, defining the type of the data
   passed to and returned from the handler.
3. Use `wxREGISTER_EXTENSION_HOOK()` to register the handler for the class in
   the same file as the one containing `wxIMPLEMENT_CLASS()` for it (and,
   possibly, other handlers for the classes deriving from it).
4. Use `wxCallExtensionHook()` wherever the new function would be called and
   use the default behaviour if it returns false.

Notes:

- Handlers can only be registered for the classes with their own class info,
  i.e. using `wxDECLARE_CLASS()` or another similar macro. All public classes
  deriving from `wxObject` have it, but this must also be ensured for all new
  classes that the application code may derive from, as adding it later
  wouldn't work for the classes compiled with the older headers.
- Handlers must be registered during the static initialization only.
- A handler returning false is equivalent to not having any handler at all,
  i.e. the handlers for the base classes are tried in this case.
- Hook ids are private, so the application code can't use them. If a hook
  should be customizable by the application, it needs to be made public and
  documented, but it's usually preferable to use an event for this, see below.


Adding new customization points
-------------------------------

If the application code needs to be able to customize some new behaviour,
consider using an event instead of adding a virtual function: adding new
event types and new event classes is binary compatible and handling events
is the usual way of customizing behaviour in wxWidgets anyhow.

New public virtual functions, which the application code would override,
can't be added in a binary compatible way and should only be added to the
development branch.


Classes which can't be extended
-------------------------------

Some classes don't derive from `wxObject` nor `wxWithExtraData` and so can't
be extended without breaking ABI at all. Notably, this is the case for:

- `wxGridCellWorker` and so all grid cell renderers and editors
- `wxPersistentObject` and all persistent objects


`wxABI_VERSION` and "forward" binary compatibility
--------------------------------------------------

As mentioned we do not support "forward" binary compatibility, that is the
ability to run applications compiled with new wxWidgets headers on systems
with old wxWidgets libraries.

However, for the developers who want to ensure that their application works
with some fixed old wxWidgets version and doesn't (inadvertently) require
features added in later releases, we provide the macro `wxABI_VERSION` which
can be defined to restrict the API exported by wxWidgets headers to that of
a fixed old release.

For this to work, all new symbols added to binary compatible releases must
be `#if`'ed with `wxABI_VERSION`.

The layout of `wxABI_VERSION` is as follows:

	20602

where

	 2     06     02
	Major Minor Release

I.e. it corresponds to the wxWidgets release in section Releases.

An example of using `wxABI_VERSION` is as follows for symbols
only in a 2.6.2 release:

	```cpp
	#if wxABI_VERSION >= 20602 /* 2.6.2+ only */
	bool Load(const wxURI& location, const wxURI& proxy);

	wxFileOffset GetDownloadProgress();
	wxFileOffset GetDownloadTotal();

	bool    ShowPlayerControls(
	  wxMediaCtrlPlayerControls flags =
	    wxMEDIACTRLPLAYERCONTROLS_DEFAULT);

	//helpers for the wxPython people
	bool LoadURI(const wxString& fileName)
	{   return Load(wxURI(fileName));       }
	bool LoadURIWithProxy(const wxString& fileName, const wxString& proxy)
	{   return Load(wxURI(fileName), wxURI(proxy));       }
	#endif
	```


version-script.in
-----------------

For ld/libtool we use sun-style version scripts.  Basically
anything which fits the conditions of being `#if`'ed via `wxABI_VERSION`
needs to go here also.

See 'info ld scripts version' on a GNU system, it's online here:
https://ftp.gnu.org/old-gnu/Manuals/ld-2.9.1/html_node/ld_25.html

Or see chapter 5 of the 'Linker and Libraries Guide' for Solaris, available
online here:
https://docs.oracle.com/cd/E19120-01/open.solaris/819-0690/chapter5-84101/index.html

The file has the layout as follows:

	@WX_VERSION_TAG@.X

Where X is the current Release as mentioned earlier, i.e. 2.  This
is following by an opening bracket "{", followed by "global:",
followed by patterns matching added symbols, then followed by "}", and then
the file is either followed by earlier Releases or ended by
a @WX_VERSION_TAG@ block without the period or Release.

The patterns used to specify added symbols are globbing patters and can
contain wildcards such as '*'.

For example for a new class member such as:

    wxFont wxGenericListCtrl::GetItemFont( long item ) const;

the mangled symbol might be:

    _ZNK17wxGenericListCtrl11GetItemFontEl

so a line like this could be added to version-script.in:

    \*wxGenericListCtrl*GetItemFont*;

Allow for the fact that the name mangling is going to vary from compiler to
compiler.

When adding a class you can match all the symbols it adds with a single
pattern, so long as that pattern is not likely to also match other symbols.
For example for wxLogBuffer a line like this:

    \*wxLogBuffer*;

Testing binary compatibility between releases
---------------------------------------------

An easy way of testing binary compatibility is just to build wxWidgets
in dll/dynamic library mode and then switch out the current library
in question with an earlier stable version of the library, then running
the application in question again.  If it runs OK then there is usually
binary compatibility between those releases.

You can also break into your debugger or whatever program you want
to use and check the memory layout of the class.  If it is the same
then it is binary compatible.
(In GDB the command x/d will show addresses as pointers to functions if
possible so you can see if the order of the functions in vtbl doesn't change.)

The recommended way of checking binary compatibility under Unix systems is to
use `libabigail` tools, see the instructions in
[how to make a new release](how-to-release.md) and `abi_check.yml` CI workflow
which checks the ABI of the stable branch automatically.

Another way to check for binary compatibility is to build wxWidgets in shared mode
and use the 'abicheck.sh --generate' script before doing your changes to generate
the current ABI (if the 'expected_abi' file is not already in the repo).
Then rebuild wxWidgets with your changes and use 'abicheck.sh' to compare the
resulting ABI with the expected one.
Note that the abicheck.sh script is in the "lib" folder.
